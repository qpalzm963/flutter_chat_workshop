# 教學腳本（10 堂全部定案）

> 依這份腳本產生 Server、講師儀表板、每堂的 starter / done 程式碼與簡報。

## 已定案

| 項目 | 決定 |
| :--- | :--- |
| 學員 | 有實務經驗的 Junior（做過 API 串接與狀態管理，沒做過即時通訊） |
| 堂數 / 時長 | 10 堂，每堂 60 分鐘以上（第 10 堂設計研討會 60～90 分鐘） |
| Starter 給多少 | UI 元件（氣泡、輸入框、連線橫幅）、最小 `Message`（sender / text / ts）、只有方法簽名的空 `ChatController`；WS 連線與所有邏輯學員自己寫 |
| 狀態放哪 | 第 1 堂起就放在 `ChatController`（記憶體 List），第 5 堂只把儲存層換成 DB |
| UI 綁定 | `ChatController` 從第 1 堂就對外提供 `Stream<List<Message>>`（最新在前），starter 的 `StreamBuilder` 已接好；第 5 堂換 DB 時 UI 不動 |
| 後端 | 全班共用一台 Server；房間由講師在儀表板分配 |
| 分房 | 第 1～4 堂可自由分（私人房 / 兩兩一組 / 大廳）；**第 5～7 堂固定兩兩一組不換房**（DB 尚無 `room_id`）；第 8 堂起自由 |
| 搞破壞權限 | 指令預設只影響自己；指定對象（`/drop Amy`、`/zombie Amy`、`@all`）只開放講師（`--admin=<名字>`） |
| `/fail` 語意 | 「收下但回條弄丟」：Server 照存照廣播、不回 ACK，用來示範冪等 |
| 開場方式 | 每堂第一張簡報：一段情境（PM / 客服 / 設計師 / 後端 / 營運說了什麼）+ 本堂目標；中途追加需求用口頭或一張簡報帶出，不另開需求單 |
| 協議演進 | 第 1 堂從純字串開始 → 升級為 JSON（`type` / `sender` / `text`）→ 第 4 堂加 `client_msg_id` → 第 8 堂加 `room_id` |

## 課程順序

| 堂 | 主題 | 階段 |
| :--- | :--- | :--- |
| 1 | 接通 + 收發（純字串 → JSON） | 純 WebSocket |
| 2 | 心跳 + 自動重連（Backoff + Jitter） | 純 WebSocket |
| 3 | 反轉列表 UI（Bottom-anchored） | 純 WebSocket |
| 4 | 樂觀更新 + ACK + 冪等 | 純 WebSocket |
| 5 | 本地 DB（SSOT） | DB + REST |
| 6 | Cursor 歷史分頁 + 進房載入最新一頁 | DB + REST |
| 7 | 斷線補洞（Delta Sync），回收第 2 堂伏筆 | DB + REST |
| 8 | 房間列表 + 多工（`room_id`、`GET /rooms`、`room_added` 推送、私聊 2 人房、DB 加 `room_id`） | DB + REST |
| 9 | 已讀 + 未讀（水位線、已讀 / 已讀 N、未讀數、進房定位第一則未讀） | DB + REST |
| 10 | 設計研討會（分組設計 + 上台報告，模擬系統設計面試） | 討論 |

心跳放第 2 堂的理由：第 1 堂要讓學員快速有成就感；第 4 堂的 ACK 逾時需要「連線可能假死」的前提；心跳與重連都是純 WS，補洞才需要 API + DB。

## Server 待改項目

- 一條 WS 承載所有房間：`/ws?user=<名字>`；前期訊息不帶 `room_id` → 送到該學員被分配的房間；第 8 堂起以訊息的 `room_id` 為準
- REST：`GET /rooms`、`GET /rooms/{id}/messages?before_seq= / after_seq= / around_seq=`
- `seq` 以房間為單位遞增
- 私聊 = 2 人房（ID 由兩人名字排序組成，如 `dm:Amy:Bob`）
- `/drop`：預設踢自己；拒絕重連只針對被踢者；機器人 3 句發在被踢者房間
- 同名已在線 → 拒絕連線
- 沒帶 `client_msg_id`（第 1～3 堂）→ Server 自動補
- 不再自動預塞歷史訊息

## 每堂結尾 10 分鐘：思考分享 / 講師補充

- **思考分享**：先出題、不給答案 → 兩人一組想 3 分鐘 → 抽 2～3 組各分享 1 分鐘 → 講師補充業界做法 2 分鐘
- **講師補充**：需要特定知識才答得出來的題目，講師直接講約 2 分鐘
- **學員端教材（簡報、分支 README）只放題目，答案只放講師筆記**

| 堂 | 形式 | 題目 |
| :--- | :--- | :--- |
| 1 | 講師補充 | WS 怎麼帶登入身分；為什麼正式環境要用 `wss://` |
| 2 | 講師補充 | 切到背景 / 被殺掉後怎麼收訊息（FCM / APNs + 延遲導航佇列） |
| 3 | 講師補充 | 插入新訊息造成畫面位移（`center` key）；圖片降採樣（`cacheWidth`） |
| 4 | 思考分享 | 使用者把手機時間調快，訊息順序會亂嗎？／訊息一萬則，收到 ACK 怎麼快速找到那筆？ |
| 5 | 思考分享 | 千人群組每秒湧入 30 則，畫面卡死怎麼辦？ |
| 6 | 思考分享 | 點擊回覆，怎麼跳到三天前那則訊息？／本地 DB 無限長大怎麼辦？ |
| 7 | 思考分享 | 離線三天，補洞要補幾千則怎麼辦？→ 分享後揭曉範圍表（Telegram），發下課後挑戰分支 |
| 8 | 講師補充 | DB 升版實務（版本號、不刪欄位、升版失敗）；為什麼不要一房一條 WS |
| 9 | 思考分享 | 千人群組的已讀，要推給幾個人？ |

（參考答案見各堂「延伸」欄與講師筆記）

## 第 10 堂：設計研討會（60～90 分鐘）

- 形式：各組認領一題 → 20 分鐘畫設計 → 每組上台 5 分鐘 → 其他組與講師扮演面試官追問 → 講師補充業界做法
- 題目：
  1. 同一帳號手機與平板同時登入（水位線記在人還是裝置？自己的訊息怎麼同步到另一台？各裝置的 outbox？）
  2. 「對方正在輸入中」（要不要存 DB？多久送一次？什麼時候消失？）
  3. 訊息編輯與刪除（`seq` 不可跳號、標記刪除、怎麼通知離線的人）
  4. 傳一支 10MB 影片（不塞進 WS、先上傳拿 URL、縮圖、上傳中斷續傳）
- 延伸閱讀（不討論）：端對端加密
- 結尾：回到最終架構圖，學員兩兩用費曼法互講整個系統

## 逐堂內容

### 第 1 堂：接通 + 收發（約 60 分鐘）✅ 已定案

| 時間 | 內容 |
| :--- | :--- |
| 0–5 | 開場提問：「要做即時聊天，你們以前會怎麼做？」引出「一直打 API 問」 |
| 5–20 | 觀念：短輪詢 / 長輪詢 / SSE / WebSocket（打電話比喻）；講師用 `curl` 現場打握手看 `101 Switching Protocols`；`ws://` vs `wss://`；用 `type` 區分事件 |
| 20–50 | 實作（私人房、兩台模擬器）：① 連線 ② 先用 `sink.add` 送純字串、`listen` 收到就顯示 ③ 發現「分不出誰講的、分不出事件種類」→ 升級成 JSON（`type` / `sender` / `text`）並解析 ④ `dispose` 收尾 |
| 50–60 | 大廳時刻：全班切大廳互傳；費曼檢核 |
| 結尾鉤子 | 講師對某位學員下 `/zombie`：畫面正常卻收不到訊息 → 引出第 2 堂 |

面試關鍵字：`Full-duplex`、`HTTP Upgrade (101)`、`Polling vs SSE vs WebSocket`、`Resource Disposal`

### 第 2 堂：心跳 + 自動重連（約 60 分鐘）✅ 已定案

| 時間 | 內容 |
| :--- | :--- |
| 0–5 | 回顧鉤子：Amy 為什麼收不到訊息？「打電話時怎麼知道對方還在？」 |
| 5–20 | 觀念：為什麼斷線了 App 不知道（切背景、電梯、NAT 逾時）；應用層 ping/pong；Exponential Backoff + Jitter；Thundering Herd |
| 20–50 | 實作（starter 提供 `ChatSocket` 空殼，連線邏輯從 `ChatController` 拆出來）：① 定時 ping、逾時未收 pong 主動斷線 ② `onDone`/`onError` 排程重連（1s→2s→4s… 上限 30s + 隨機毫秒）③ 連上後重置次數 ④ 對外發連線狀態（橫幅已接好）⑤ `dispose` 清 Timer |
| 50–60 | 驗收：自己 `/zombie` → 15 秒內自動連回；講師 `/drop @all` → 儀表板「重連時間軸」對比有／無 Jitter |
| 結尾鉤子 | 斷線期間講師在大廳講話，連回後看不到 →「訊息去哪了？」留到第 7 堂；狂傳 20 句被鍵盤擋住 → 引出第 3 堂 |

- 心跳參數：課堂用 10 秒 ping、5 秒 pong 逾時；講義註明正式環境通常 25～30 秒
- 儀表板需求：重連時間軸（每位學員重連時間點，可對比有／無 Jitter）

面試關鍵字：`Zombie Connection`、`Heartbeat (Ping-Pong)`、`Exponential Backoff + Jitter`、`Thundering Herd`

### 第 3 堂：反轉列表 UI（約 60 分鐘）✅ 已定案

| 時間 | 內容 |
| :--- | :--- |
| 0–5 | 痛點演示：一般 `ListView` 進聊天室從頂部跳到底部閃一下；新訊息被鍵盤擋住 |
| 5–20 | 觀念：Bottom-anchored vs Top-anchored；`reverse: true` 原理（index 0 在底、offset 0 就是底部，鍵盤彈起自然上推）；列表虛擬化（為什麼要 `ListView.builder`） |
| 20–50 | 實作：① `ListView.builder(reverse: true)` ② 用 `ScrollController` 判斷是否在底部 ③ 往上翻時有新訊息 → 不拉回、顯示「有新訊息 ↓」（提示元件與顯示/隱藏邏輯都由學員自己寫）④ 點提示或自己送出 → 捲回底部 |
| 50–60 | 驗收：進房直接在底部不閃；鍵盤上推；往上翻時鄰座傳訊息只出提示；講師灌 1000 則 + 效能圖層仍順暢 |
| 延伸 | `center` key 避免插入位移；`cacheWidth` 圖片降採樣 |
| 結尾鉤子 | 講師開「全域延遲 2 秒」→ 自己的訊息要等 2 秒才出現 →「LINE 為什麼秒出現？」引出第 4 堂 |

- 排序：`ChatController` 的 Stream 直接輸出「最新在前」，第 5 堂 `ORDER BY seq DESC` 順序一致，UI 不用改
- 儀表板需求：對指定房間灌 N 則訊息；全域延遲開關

面試關鍵字：`Bottom-anchored vs Top-anchored`、`Layout Shift`、`List Virtualization`

### 第 4 堂：樂觀更新 + ACK + 冪等（約 60 分鐘）✅ 已定案

| 時間 | 內容 |
| :--- | :--- |
| 0–5 | 回顧鉤子：全域延遲下送出很卡；講師在儀表板把 Server 切到「ACK 模式」（不再回送發送者、改回 ACK） |
| 5–20 | 觀念：Optimistic UI；狀態機（sending → sent / failed）；ACK 與 `seq` 首次登場（Server 核發）；掛號信故事講冪等 |
| 20–35 | 實作（先故意做錯）：① `Message` 加 `clientMsgId` / `status` / `seq` ② 送出先插入 sending 再送 JSON ③ ACK 用 `clientMsgId` 找到那筆 → sent + `seq` ④ 5 秒沒 ACK → failed ⑤ 點紅點重試，但**重試產生新 UUID** |
| 35–45 | 翻車現場：`/fail` 後重試，同組夥伴看到兩則一樣的訊息 → 學員自己找原因 |
| 45–55 | 修正：重試沿用同一個 `clientMsgId` |
| 55–60 | 驗收：`/delay` 秒上屏 3 秒後變勾勾；`/fail` 變紅點、連點重試不重複 |
| 延伸 | 手機時間被調 → 排序只信 `seq`；`indexWhere` O(n) → Map 索引 |
| 結尾鉤子 | 殺掉 App 重開，訊息全不見 → 指著能力演進表引出第 5 堂 |

- starter 的氣泡已有三種狀態圖示，學員只傳 `status`
- 斷線時送出的訊息：第 4 堂只做「逾時變紅點、手動重試」；自動補送（outbox）放第 7 堂

面試關鍵字：`Optimistic UI`、`ACK`、`State Machine`、`Idempotency (client_msg_id)`

### 第 5 堂：本地 DB（SSOT）（約 60 分鐘，兩兩一組固定房）✅ 已定案

| 時間 | 內容 |
| :--- | :--- |
| 0–5 | 回顧鉤子：殺掉 App 重開，訊息全不見 |
| 5–20 | 觀念：SSOT（唯一的筆記本，UI 只看 DB、WS 只寫 DB）；單向資料流；`client_msg_id` 主鍵去重、`ORDER BY seq` 排序；選 sqflite 不選 Drift 的理由 |
| 20–50 | 實作（starter 已建好資料表與查詢）：① Controller 的記憶體 List 換成 `LocalMessageStore` ② 學員自己寫 upsert（`INSERT … ON CONFLICT(client_msg_id) DO UPDATE`）與變動通知 ③ 送出寫 sending、ACK 更新、廣播 upsert ④ Stream 改訂閱 DB（UI 不改）⑤ 啟動時殘留 sending → failed |
| 50–60 | 驗收：殺掉 App 重開秒開；講師在儀表板暫時拒絕某學員連線，重開 App 仍看得到所有訊息並顯示斷線橫幅 |
| 延伸 | 千人群組湧入 → 記憶體緩衝佇列 + 每 200ms 批次寫 DB |
| 結尾鉤子 | 刪掉 App 重裝（模擬換新手機）又是空的 →「Server 明明有存，為什麼拿不到？」引出第 6 堂 |

- 儀表板需求：暫時拒絕某學員連線 N 秒（第 5 堂驗收離線秒開、第 7 堂測補送）

面試關鍵字：`SSOT`、`Unidirectional Data Flow`、`Upsert`、`client_msg_id vs server_seq_id`

### 第 6 堂：Cursor 歷史分頁 + 進房載入最新一頁（約 60 分鐘）✅ 已定案

課前：講師用儀表板替每個兩人組房間灌 300 則。

| 時間 | 內容 |
| :--- | :--- |
| 0–5 | 開場情境：PM「換新手機看不到以前的對話」 |
| 5–20 | 觀念：WS（即時）與 REST（歷史 / 大量）分工；Offset vs Cursor —— 先用簡報動畫呈現「新訊息插入後第 2 頁整個位移、同一則出現兩次」，再用 `curl` 1 分鐘現場證明 |
| 20–45 | 實作（starter 提供 `HistoryApi` 與頂端載入指示元件）：① 進房 DB 為空 → 抓最新一頁（50 則）寫 DB ② `watchMessages` 加 `limit`，UI 只看本地視窗 ③ 偵測快捲到頂 → **兩段式分頁**：先擴大本地視窗，本地不夠才以最舊 `seq` 呼叫 `before_seq` 寫 DB ④ 載入中旗標 + 沒有更早訊息的判斷 |
| 45–55 | 驗收：重裝 App 進房出現最新一頁；往上滑無縫載入不重複不跳動 |
| 延伸 | 點擊回覆跳原訊息（同第 9 堂 `around_seq` + 錨點）；回覆存快照；斷層追蹤；本地容量上限（每房只留最新 N 則，更舊的需要時再向 Server 拿） |
| 結尾鉤子 | 講師暫時拒絕某學員連線，夥伴趁機傳 3 句，連回後看不到 → 第 7 堂 |

- 課堂重點：DB 不為空時不抓最新一頁，否則中間會出現 App 不知道的斷層（留給第 7 堂）
- 每頁 50 則
- 「訊息太多」四層：網路分頁（本堂）、本地查詢視窗（本堂）、畫面虛擬化（第 3 堂）、本地容量上限（延伸）
- 現有 step-5 的 `SELECT * FROM messages` 全表查詢要改成視窗查詢

### 第 7 堂：斷線補洞 + 補送（約 60 分鐘）✅ 已定案

| 時間 | 內容 |
| :--- | :--- |
| 0–5 | 開場情境：客服「出電梯漏訊息」「捷運上傳的訊息沒送出」；回收第 2 堂伏筆，指著能力演進表最後一個 ❌ |
| 5–20 | 觀念：Delta Sync（本地最新 `seq` → `after_seq` 一頁頁補到底）；回答第 6 堂「為什麼 DB 不空不抓最新一頁」；Outbox；補送靠第 4 堂冪等不怕重複；補送依建立時間排序（`seq` 由 Server 收到時核發） |
| 20–50 | 實作：① Controller 監聽連線狀態，每次連上（含 App 剛啟動）觸發 ② 補收：`after_seq` 分頁寫 DB 直到不足一頁 ③ 補送：DB 中所有未送達（sending + failed）依建立時間帶原 `clientMsgId` 重送並重設 ACK 逾時 |
| 50–60 | 驗收：① `/drop` 後機器人 3 句自動補回 ② 講師拒絕連線 30 秒期間送 3 則，解除後自動送出、夥伴依序收到不重複 ③ 離線送出後殺 App，解除封鎖再開仍送得出去 |
| 延伸 | 多媒體分流；Gap Detection；**主角：範圍表（Telegram 做法）**——離線太久的三種策略（全補 / 清掉重抓 / 範圍表）比較；範圍表一次解決第 6 堂跳回覆、第 7 堂大斷層、第 9 堂未讀定位；未讀數不必下載訊息；`seq` 不可跳號（刪除用標記） |
| 結尾鉤子 | PM + 營運：要私訊和群組、活動拉群 → 講師一鍵拉群但學員 App 沒房間列表看不到 → 第 8 堂 |

- 補送範圍：sending 與 failed 都自動補送；紅點語意改為「目前還沒送達」，點擊立刻重送
- 課後挑戰分支：已載入範圍表（`loaded_ranges`），重連只抓最新一頁、滑到洞的邊緣才補該段、區段合併

### 第 8 堂：房間列表 + 多工（約 60 分鐘）✅ 已定案

架構轉折：連線從聊天頁提升到 App 層級（全 App 一條），每個房間的 `ChatController` 只從這條連線過濾自己房間的訊息。

| 時間 | 內容 |
| :--- | :--- |
| 0–5 | 開場情境：PM 要私訊和群組；營運要活動拉群 |
| 5–20 | 觀念：為什麼不能一房一條 WS；訊息帶 `room_id`；房間列表 API；Server 推送 `room_added`；私聊 = ID 固定的 2 人房；本地 DB 升版 |
| 20–50 | 實作（starter 提供房間列表 UI 與 DB 升版骨架，`onUpgrade` 內 SQL 留 TODO）：① DB 升版：`messages` 加 `room_id` + 索引、新增 `rooms` 表、舊資料歸到原兩人組房 ② `ChatSocket` 移到 App 層級；`ChatController` 每房一個、依 `room_id` 分流，ACK 依 `clientMsgId` 對應 ③ 送出帶 `room_id`，查詢 / 分頁 / 補洞加房間條件 ④ 房間列表：啟動 `GET /rooms` 寫 DB、UI 訂閱 DB；`room_added` 新增；他房新訊息更新預覽並置頂 ⑤ 私聊：選線上學員 → 算出 `dm:A:B` → 直接送出 |
| 50–60 | 驗收：講師一鍵拉 3 人進群，列表即時出現；群裡發言 → 置頂 + 預覽；和夥伴私聊；升版後兩人組舊訊息還在 |
| 延伸 | DB 升版實務（版本號、不刪欄位、升版失敗）；為什麼不要一房一條 WS |
| 結尾鉤子 | PM：「我怎麼知道對方看了沒？」→ 第 9 堂 |

- 重連策略：只重拉房間列表（含各房最新 `seq`，更新預覽與未讀數），只對目前開著的房間補洞，其他房點進去再補
- 私聊建立：客戶端算出 `dm:A:B`，第一則訊息送出時 Server 自動建房，不另設 API

面試關鍵字：`Multiplexing`、`Schema Migration`、`Server Push`、`Lazy Sync`

### 第 9 堂：已讀 + 未讀（約 60 分鐘）✅ 已定案

| 時間 | 內容 |
| :--- | :--- |
| 0–5 | 開場情境：PM「要有已讀」 |
| 5–20 | 觀念：水位線（每人每房一個 `last_read_seq`、只能前進、Debounce 回報）；一對一「已讀」vs 群組「已讀 N」（水位線 ≥ 該 `seq` 的人數）；未讀數 = 房間最新 `seq` − 我的水位線 |
| 20–50 | 實作（starter 提供已讀狀態表、氣泡已讀標籤位置、未讀分隔線元件）：① 捲動時算畫面可見最大 `seq`，Debounce 500ms 經 WS 回報 `{"type":"read","room_id","seq"}`，只往前推 ② 收到他人已讀更新寫 DB，自己的訊息顯示「已讀」/「已讀 N」③ 房間列表未讀數 ④ 進房定位第一則未讀（`center` key 錨點）+「以下為未讀訊息」分隔線 +「跳到最新 ↓」 |
| 50–60 | 驗收：儀表板即時看到水位線隨捲動前進；夥伴讀了顯示「已讀」；3 人群組「已讀 2」；講師設 Amy 已讀到第 50 則再灌 300 則 → 列表未讀 300、進房停在分隔線 |
| 延伸（參考答案） | 群組已讀廣播量（fan-out）：只推給發送者、Server 節流、改為主動拉、大群關閉已讀 |
| 結尾 | 能力演進表全打勾；思考分享：千人群組的已讀要推給幾個人？ |

- 已讀定義：訊息實際出現在畫面上才算（不採一進房全部已讀）
- 未讀定位不需 `around_seq`：第 7 堂補洞已把開著房間的漏訊補進本地，只需決定畫面從哪開始；例外是新裝置首次進房、第一則未讀不在本地 → 停在底部並顯示「上方還有 N 則未讀 ↑」
- `around_seq` 只用在範圍表課後挑戰

面試關鍵字：`Read Watermark (High-water Mark)`、`Debounce`、`Fan-out`、`Unread Anchor`
